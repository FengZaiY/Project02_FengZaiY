## 1. 未确认上传的附件分块缺失后，后续发布错误复用

- 位置：`src/core/current-sync.mjs:112`、`:142`、`:204`、`:221`。
- 触发：首次发布生成成功，尚未确认上传；某附件分块不在传输目录。源电脑原件仍完整，修改笔记后再次发布。
- 原因：`knownAssets()` 无条件纳入本机最近发布及已知远端清单；只要哈希在其中，所有分块就标为 `reusable`。发布阶段既不重新生成缺失的可复用分块，也不要求该分块已有上传确认。
- 实测：第二次任务返回 `complete`，本机原件存在，缺失分块没有重新生成；另一台隔离工作区完整导入时报 `ENOENT`，笔记未入库。
- 影响：原件仍在却不能靠重新发布恢复传输，用户可能反复发布、下载但始终无法完整导入。这里的 `complete` 是交接文件生成完成，不能表述成系统谎报了云端上传成功；缺陷是生成阶段漏掉了所需对象。
- 建议：区分“已知描述”“本机已校验对象”“用户确认上传/有效接收证据”。缺失且没有安全传出证据的分块应从本机原件重新生成，无法生成则阻止发布并列出缺项。已明确仅释放本地、且具备确认依据的云端对象仍可复用，不要求重新下载所有历史对象。无内容变化的再次发布也需提供缺项修复路径。
- 后续回归：跨两次发布的缺块、无变化重试、分批确认、已确认云端对象仅释放本地、取消/中断和原件也缺失。

此复现只删除隔离传输目录中已知的测试分块，模拟缺失状态；未操作百度客户端或真实文件。

## 2. 存储位置重启绕过进行中导入保护

- 位置：`src/desktop/main.mjs:130`；界面调用入口 `web/app.js:1456`，与普通退出的 `src/desktop/exit-check.mjs:3` 对照。
- 触发：已有待生效的存储位置变更，此后导入原文件尚未完成，调用“重启并应用”。
- 原因：该分支只检查同步、目录整理和持久化笔记 dirty 状态，未检查 `service.imports`、永久清理及其他活动 IPC；通过定时器直接执行 `app.relaunch()` / `app.exit(0)`，没有复用普通退出握手。界面的 `requireStorageSaved()` 也没有导入保护。
- 实测：隔离 Electron 中暂停真实 `assetImport` 的文件复制，调用真实 `storageRestart` IPC，返回 `true`，随后调用了重启及退出函数。测试拦截这两个函数，仅记录调用；释放复制后导入正常结束，没有真正中断进程或迁移资料。
- 影响：用户通过目录设置重启可能截断尚未完成的导入/清理任务。普通退出已有的保护在此入口未生效。没有将此复现夸大为已证明现存笔记丢失。
- 建议：与普通退出共用活动任务检查、界面保存确认和最后一次状态复核，在确认后冻结新增操作，再等待受控关闭完成后重启。不能只在点击按钮时检查一次。
- 后续回归：导入、永久清理、慢 IPC、确认后新写入、未保存偏好、取消及失败；重启后检查实际数据库和原件。

## 3. 普通附件预览没有核验实际内容和大小

- 位置：`src/core/service.mjs:288`；调用方 `web/app.js:1296`。
- 触发：已导入的本机原件被外部程序修改或损坏，然后从原附件/资料预览打开。
- 原因：`assetContent` 只检查绑定、存在性及数据库登记大小，直接 `readFileSync` 并转 Base64；没有验证实际文件大小、哈希、链接路径或已删除/冲突状态。MCP 附件读取及媒体流接口已有更严格校验，行为不一致。
- 实测一：16 字节原件替换为同长度不同内容，预览正常返回替换后的内容，没有完整性错误。
- 实测二：同一记录登记仍为 16 字节，本机文件扩展到 25 MiB，接口仍完整读取并返回，绕过 24 MiB 预览限制。
- 影响：用户可能把被修改的内容当成已校验资料；原件实际大于登记值时，预览的内存和同步读取成本也失去限制。
- 建议：复用统一附件读取校验，验证当前记录状态、受允许的本机绑定、实际大小和哈希，保证验证和读取对应同一文件。避免先全量读取后才判断上限。
- 后续回归：同长度损坏、文件变大、路径链接、已回收/冲突、缺失，以及验证期间文件发生变化。

## 4. 凭证和 Skill 复制仍会被桌面权限策略拒绝

- 位置：`web/app.js:797`（访问凭证），`web/skill-manager.js:89`（Skill 文件）。`web/app.js:1424` 的存储路径复制也使用同一路径，属于应一并检查的同类调用；本轮未单独点击复现路径复制。
- 触发：源码桌面程序中新建隔离授权，点击“复制凭证”；或在设置的 Skill 文件页点击复制。
- 原因：这两个入口直接调用 `navigator.clipboard.writeText()`，未复用已经用于 MCP 地址和配置的 `copyText()` 兼容处理。桌面权限策略没有为这些调用放行。
- 实测：两处均提示 `Failed to execute 'writeText' on 'Clipboard': Write permission denied.`；真实 MCP 地址复制修复并未覆盖这些入口。
- 影响：一次性凭证复制失败，用户仍可显示后手动选择，但配置体验受阻；关闭弹窗后不能再次获取原凭证。
- 建议：统一复制 helper；自动复制全部失败时选中可见内容，提示手动复制，不能误报成功。无需放宽桌面全局权限。凭证只在本次用户操作使用，不写日志或报告。
- 后续回归：正常复制、Clipboard API 拒绝、兼容复制失败、选区恢复、一次性凭证关闭清理。

## 5. 视频每次范围请求都重新读取整个文件

- 位置：`src/core/media.mjs:22`。
- 触发：视频读取片段、拖动进度，或重复请求预览；HEAD 请求也会先计算整份哈希。
- 原因：每个请求在解析 Range 之前，完整流式计算 SHA-256，没有复用与文件状态绑定的校验结果。
- 实测：8 MiB 隔离文件，连续 3 次请求各 1 KiB，实际读取合计 25,168,896 字节，而响应总计仅 3,072 字节。测试用例只验证媒体接口的读取量，不依赖视频编码解码。
- 影响：大视频反复定位或预览产生与原件大小成正比的额外磁盘读取，响应必须等待全量校验完成。本轮未对 GB 级真实视频做速度测试，不承诺某个秒数。
- 建议：保留完整性保护，引入受文件身份、大小和修改状态约束的已验证结果缓存；变化立即失效。无效 Range/HEAD 的处理也应避免无意义重复读盘，不可直接删除哈希校验来换取速度。
- 后续回归：重复 Range、HEAD、校验缓存失效、同大小文件被替换、读取中释放保护及请求取消。
