# Architecture

## FengZai·Y personal management (2026-10-27)

The Windows local workspace now has five business areas: knowledge/notes, materials, accounts/subscriptions, finance, and tasks. The Electron display name, window title and installer product name are FengZai·Y. Package identity `studyself`, appId `cn.studyself.desktop`, the existing userData/workspace anchor, `studyself://` links, media protocol, MCP tool prefix and environment variables remain stable. This change does not update installed applications or external Skill copies.

`personal-schema.mjs` defines independent entities: materialCollection, personalProject, personalTask, loginAccount, subscription, moneyAccount, moneyEntry, moneyBudget, vaultConfig, vaultSecret and changeBatch. Business records use `__personal__`; independent assets use `__materials__`. Neither scope creates a knowledge library. The retired AI `task` remains retired. Strict fields, integer amounts, dates, references, hierarchy and relationship validation are shared by trusted UI and Agent writes. Existing IDs, event checksums and history are retained.

`PersonalManager` handles nonsecret CRUD, local form drafts, reports, subscriptions and CSV. Monetary values use currency-specific minor-unit safe integers; decimal parsing and manual CNY conversion use BigInt and round once to the target minor unit. A transfer is one immutable entry with both accounts and amounts, validated and committed atomically; it changes balances but not income/expense. Refunds reference an expense and cannot cumulatively exceed it. Opening balances and valuation adjustments are separate fields/record kinds. Balances and reports derive from effective records, skipping conflicting or invalid entries and returning explicit incomplete reasons, including missing FX. Budget execution is per month/category/currency. Subscription payment and schedule advancement share one transaction, with a deterministic subscription/period entry ID. CSV is limited to 5 MiB/2,000 rows, previewed with mapping and duplicate checks, then revalidated and committed as a batch.

`Store.change` records before/after heads for each object in a changeBatch. Nested operations share a batch; nested transactions use savepoints and restore the captured changes on rollback. User saves/imports and Agent writes retain a source label. `ChangeHistory` lists batches and differences; undo creates new revisions and a reversal batch. It checks exact current heads, original version availability, conflicts, dirty forms and new references. Linked modifications reverse together. Original history remains. Secret differences are redacted; secret undo requires an unlocked vault, and configuration/master-password changes use the recovery workflow. These are history operations, not filesystem undo or whole-workspace snapshots.

### Password vault boundary

`PasswordVault` owns an independent 256-bit random data key, with AES-256-GCM envelopes and context-specific authenticated data. A versioned scrypt descriptor (N=131072, r=8, p=1, 16-byte random salt) derives the master wrapping key. A separate random 256-bit recovery key wraps the same data key; setup completes only after recovery-key confirmation. Sync and device credential keys are never reused. Derived buffers and in-memory data-key buffers are cleared on lock. Idle timeout is ten minutes; desktop lock-screen, suspend and close lock the vault. Pending setup also expires.

Account public metadata is a loginAccount; password/recovery codes/secret notes are a vaultSecret encrypted for that account. UI secret edits can persist only as a local encrypted `vaultDraft:<accountId>` entry. These drafts block account/secret deletion and remote erasure until handled. Plaintext is not written to normal drafts, events, projections, audit, exports or Agent responses. Renderer fields are populated through input values and cleared when closing/locking; no secret is interpolated into HTML attributes. `SecretClipboard` clears only the value it copied after 30 seconds, retaining later unrelated clipboard content.

Ciphertext can be received while locked. Secret conflicts require selecting and saving a version after unlock. Independent vault initializations are configuration conflicts, not last-writer-wins: credentials for every branch are required, historical data keys are authenticated and rewrapped under a fresh root key, and a new recovery key must be confirmed. This preserves old secret history while merging configuration heads. A configuration-head change locks an active session. The Agent has no vault methods, raw Service forwarding or access to vaultConfig/vaultSecret/changeBatch.

### Materials and local files

New imports use `<workspace>/.fengzai-y/materials/<sha-prefix>/<sha256>`. A device ownership marker protects the managed directory. Collection membership is many-to-many metadata; notes, tasks, entries and subscriptions reference stable asset IDs. The old library domain remains queryable through original ownership and libraryDomains. Duplicate merge retains collections/tags and rewrites supported public business references atomically; history remains protected.

`MaterialCenter` previews legacy asset counts, bytes, source/target paths and blocking issues. Confirmed jobs persist rows and completed IDs locally. Copy uses a temporary file, hash/size verification and fsync, followed by exclusive publication, version-checked metadata and binding in a transaction. Only then is a trusted old managed original queued for the existing reference/hash-checked cleanup. Interrupted, occupied, low-space and verification-failed entries retain progress for retry. External import sources, unknown files, changed originals and hand-edited projections are retained. Root relocation remaps pending migration paths along with asset bindings and local links. New sync receptions assemble in received-objects, then exclusively publish the verified original into the central hash directory before binding; changed targets are never overwritten. Existing verified legacy bindings remain available and are centralized through the migration preview. The UI shows actual locations.

Knowledge projection directories retain note bodies and stable asset references. Finance and password data do not receive plaintext projections. The SQLite database stays local and outside the encrypted directory transport. Explicit desktop exports default to `.fengzai-y/exports` through the native save dialog; users can choose another destination. The same workspace ownership marker protects that directory, filenames are sanitized and preparing a destination never overwrites an existing file. Browser previews use browser download settings. Incoming chunks, managed originals, note projections and user-selected exports have separate lifecycles; no migration deletes an entire directory recursively.

### Sync and frontend integration

The trusted renderer checks `Service.state().uiProtocol` against `ui-protocol.mjs` before loading navigation or business drafts. A missing or incompatible protocol stops initialization without writing workspace state. `startup.js` retains a visible Chinese recovery page for compatibility, transport and other initialization errors; details use textContent and reload fetches a fresh page and local authorization token. This runtime contract is independent of product version and sync format. Browser preview serves built files from disk while Node retains loaded modules: changing backend source therefore requires restarting the original preview process with the same workspace anchor, then refreshing the browser. Building the UI alone is insufficient.

New business entities, operation batches, centralized material metadata and associated erasures require **format 7**. Current clients still read earlier formats. Import rejects new entity data disguised as an older format before committing records. Older clients must reject format 7 rather than partly apply it; every participating computer must upgrade. Ciphertext, batches and reversals use the existing immutable-record conflict and integrity pipeline. Local drafts and paths do not become shared state.

`personal-pages.js` provides compact secondary navigation, lists/forms, links, report and vault workflows. Five fixed primary navigation entries sit above the tool area; knowledge retains tabs, hierarchy and split reading. Device management is under sync. Per-board filters, selection, scroll and last location stay local. Nonsecret form drafts survive switching/restart, serialize saves and preserve typing during requests. All boards join the existing close/install/sync protection. Search is local to the board by default, with an explicit nonsecret global search. Conflicts open a comparison before editing. UI/API version checks remain authoritative; a label does not imply remote cloud upload, payment or successful migration.

New named MCP tools cover tasks/projects, account metadata, subscriptions/payment recording, money accounts/entries/budgets/reports, collections, material properties and public business batches. All writes retain grant revalidation, request receipt, preference version and base heads in the same transaction. Revocation immediately removes the grant and its receipts/audit; already-started requests recheck before execution. The bundled `studyself-organize` Skill describes the expanded public boundary, while system configuration, secret operations, permanent deletion and undo stay in the trusted UI.

## Local business workflow guards

Subscription payments and CSV rows use deterministic ledger identities. A user undo leaves a deletion revision: a new payment or import may reuse that identity only when its current head is unconflicted and deleted. CSV preview tokens cover those heads, so an old preview cannot restore an identity changed by a later undo. Purged identities remain blocked. Changing an account opening date checks existing entry branches, including incoming transfers, to avoid excluding valid entries from derived balances.

Business forms serialize commits, retain edits made while a request is pending and ignore detached form events. Recycled details use the fetched record status, disable edits and expose restoration. Secret submission disables its controls until completion; failed saves retain encrypted drafts. Undoing a first secret revision yields an empty default editor with current heads while explicit historical ciphertext remains available only after unlocking.

MCP preserves known business error codes for reference, unsaved, duplicate, purged, busy and retired guards; unknown errors remain sanitized. The distributed client reads structuredContent.value when present, otherwise parses the JSON text result directly. These guards do not change event hashes, identities, encryption or synchronization formats.

## Sync workspace interface

`web/sync-model.js` derives available operations from publication, device and local request state. `web/sync-panel.js` owns the send/receive panels, while `sync-pages.js` retains device management and `app.js` owns page composition and configuration. These UI changes do not change synchronization formats or core authorization.

Sending and receiving are separate directions. File generation, user-confirmed cloud upload, merged records and original-file completeness remain distinct evidence. Frozen tasks show their cutoff time; progress reserves a step for final manifest publication. A previously merged manifest does not prove its originals are available. Receiving exposes full versus metadata-only selection with device-role restrictions, and links to conflicts while preserving both versions. Configuration opens for first use and is folded after pairing; space options, task details and diagnostics remain available on demand.

Each sync action is guarded through its confirmation dialog and request. Updates replace only changed sync sections, retaining configuration inputs, focus and expanded details. Status responses are bounded by the current host element and sequence; completion after navigation must not recreate the note editor. Post-import status failures report that content was already received. Core transactions, role validation, unsaved-edit protection and explicit upload confirmation remain authoritative.

Trusted `syncDisconnectPreview`/`syncDisconnect` detach only the local connection. The preview token covers the local binding revision, channel/directory, job, publication summary and device-management revision. Configuring a binding creates a fresh local revision, including when reconnecting with identical values, so an old confirmation cannot detach a new binding. Running sync, imports and directory maintenance block disconnection. One SQLite transaction cancels an unfinished publication in its original channel and removes the active pairing secret, directory, binding revision and last scan reports; failure rolls back both cancellation and configuration removal. Knowledge, dirty tabs, original files, receive checkpoints, namespaced sync metadata and shared device control remain intact. Reconnection replans cancelled work and retains suspension/role policy. There is no filesystem deletion, remote notification, shared-key revocation, Baidu action or external Agent capability. A primary or pending-transfer warning explains that shared roles do not change.

## Verified attachment reads and desktop actions

`asset-reader.mjs` shares the trusted preview and media read boundary. It rejects missing/deleted/conflicting records, checks the local binding and non-symlink path, and holds an active-read reference through completion/cancellation. Allocation is bounded by the registered and actual file size. Reads use one open handle; descriptor/path identity and record heads are rechecked after asynchronous operations. Ordinary preview hashes the exact returned bytes. Media verification uses a per-store, 128-entry in-memory LRU keyed by local path and expected SHA-256, stamped with device/inode, size, nanosecond mtime and ctime. Changed or unavailable identity forces a full hash. Invalid ranges fail before hashing; repeated valid Range/HEAD requests reuse only an unchanged verified file. This cache never proves cloud upload or replaces incoming assembly verification.

Clipboard callers share `copyVisibleText`: Clipboard API, then a temporary selection within the active modal (or document body), then explicit manual selection of the still-current visible value. Credential manual fallback reveals the field only following the user's copy action; closing the dialog clears its value. No desktop clipboard permission expansion or new Agent capability is introduced.

## Retired interactive reading

Interactive reading, its page preview/designer contract, worker and dedicated dependencies have been removed. New note/draft/proposal writes reject `presentation`, including null. The ordinary editor retains rich body content, media, diagrams, attachments and history. Agent bootstrap no longer advertises page capabilities, and the bundled Skill only describes body and knowledge-structure workflows.

`retired-presentation.mjs` is migration compatibility, not a rendering runtime. Startup validates old revisions before stripping only page fields from note/draft data, proposal candidates and workspace drafts. The transaction preserves event/entity IDs, parents, non-page fields and accepted draft-result references. It adds `retiredPresentation` containing the original hash and calculates a new checksum over the sanitized representation. This explicitly authorized payload retirement is a narrow exception to immutable historical hashes; it does not repair invalid checksums. Duplicate handling compares both original identity and sanitized hash. Erasure receipts retain the original identity hash, so prior deletion receipts still prevent resurrection.

Pending/rejected events, cached records and Agent idempotency results are sanitized in the same startup transaction. Affected frozen publication plans are cancelled rather than reused with stale object hashes. Unsaved body text survives. Failed migration rolls back; database compaction and tracked local projections use the existing retry and ownership checks. Imported old revisions undergo the same original validation and deterministic conversion before persistence. Imported originals are retained, including files formerly referenced only by page designs.

CurrentSync publishes format 6 when histories contain converted records. Old encrypted history objects are validated, replaced with sanitized encrypted objects, then linked by an authenticated format-2 replacement index before their local transport copies are removed. The index identifies the page retirement and may have no erasure receipts; ordinary deletion replacement format 1 remains supported. Failed writes preserve the original for retry. New clients can follow older manifests and replacement chains; all syncing computers must upgrade. This does not remove Baidu historical/recycle-bin copies, unknown exports or installed application data outside the running workspace.

## Process boundaries

`src/core` is independent of Electron. Each device owns one SQLite database with WAL journaling. The Windows renderer has no Node integration. A sandboxed preload exposes only a bounded RPC entry point; the main process checks the sending frame. Windows secrets use `safeStorage`. The browser development adapter binds only to loopback, checks Host and Origin, and requires a random per-process token on mutation requests.

The desktop installer preserves application data and uses a stable application ID. Online updates use electron-updater with NSIS and a fixed public GitHub or HTTPS provider embedded in package metadata by `scripts/release-config.mjs`. The default shares the user-provided public `FengZaiY/Project02_StudySelf` repository; release upload and actual installation remain separate work. The app exposes no public network server. An explicitly enabled Agent listener is loopback-only and exists in both desktop and development-preview processes.

`src/desktop/updates.mjs` owns an explicit check/download/install state machine. Automatic startup checks never download; ordinary quit never installs. Settings render plain-text release notes and progress without replacing note editors or preference fields. Update RPC is confined to sender/frame-checked desktop IPC, absent from Service, browser preview and Agent dispatch. Startup-check preference is local to Electron userData, outside shared workspace entities. Developer runs do not initialize an updater.

Installation requires renderer unsaved-state checks and persisted workspace flush, then a native confirmation and main-process idle checks (other RPC, synchronization, imports, local maintenance, active file reads, pending storage migration). The renderer is temporarily inert during this handshake. Main-process writes are gated, background maintenance and Agent listener stop before invoking the installer; standard quit closes SQLite and releases the workspace lock. Synchronous installer errors release the gate and restart local services. SHA512 download validation is delegated to electron-updater; publisher verification applies when signing is configured in the release. No unsigned payload is described as publisher-verified. Actual OS installer, elevation, signing and migration across released versions require separate release acceptance.

## Emptying the recycle bin

`src/core/trash.mjs` provides trusted-UI-only preview and execution. Scope is one library or the workspace, independent of list search and pagination. It examines all current branches, recycled references, proposal targets, rich references and unsaved local drafts. Conflicts, active file reads and surviving incoming references protect a target. Protection propagates through candidate dependencies; an eligible group may be cleared together. A preview digest is recomputed inside the write transaction, so changed candidates or protection reasons invalidate confirmation. All deletion records and local tab cleanup commit or roll back together.

Clearing now removes entity payloads from `events`, `heads`, pending/rejected records and matching Agent response caches. `erasures` stores independent receipts with entity/type/device identifiers and observed revision ID/hash pairs, never body text or titles. Existing event hashes are not rewritten. The receipt and persistent file-cleanup allowlist commit together. Existing logical `purged` data remains compatible and can be explicitly selected again for physical cleanup. All surviving historical references, not just current heads, protect dependencies; exclusively referenced assets are included in the confirmation.

`permanent-files.mjs` deletes only checksum-matching managed originals and tracked projections, preserving external sources and changed files. Per-file outcomes survive restart. SQLite secure_delete, checkpoint and VACUUM reclaim payload pages; failures remain visible and retryable. This is normal deletion, not forensic sanitization. Legacy directory ownership uses persisted library mappings and markers even after the last visible record disappears. Old migration copies require a separate confirmed allowlist; unknown old-workspace edits block cleanup and untracked extras survive.

With erasures, CurrentSync emits format 4 self-contained manifests in the existing channel plus authenticated `.sserasure` receipts. Import reads deletion receipts before requiring original assets. Known old events are discarded; unknown concurrent revisions or surviving references block import without deleting local edits. `erasure-sync.mjs` rewrites mixed encrypted history parts to retained events and publishes an authenticated `.ssreplacement` chain before deleting old objects. Original device manifests need not be overwritten. Exclusive asset chunks are removed only when readable local manifests/objects do not retain their hash; absent or corrupt history blocks that cleanup. New devices follow replacements and receipts; older clients must upgrade. Client-mediated deletion of current transport files is distinct from deleting Baidu history or recycle-bin copies, which remains manual. Offline/partial transport and filesystem failure are reported rather than treated as cloud completion. External Agent permissions are unchanged.

## Document interactions

`web/mindmap-editor.js` provides a dedicated mind-map canvas and consistent inline SVG preview. It uses Mermaid's installed parser through `getDiagramFromText` and D3 hierarchy for deterministic tree placement, not a hand-written Mermaid parser. D3 hierarchy 3.1.2 was already transitive and is now an explicit pinned development dependency. `web/mindmap-model.js` keeps the original per-topic declaration until that topic is renamed; changed labels use Mermaid numeric entities. The Mermaid 12 DB entity adapter is covered by punctuation, literal HTML, emoji and multiline round-trip tests.

Mind maps remain v1 `diagram` blocks with `source` and `label`. Optional layout/palette/collapse state is encoded in one `%% studyself-mindmap:` comment, which older Mermaid readers ignore. Collapsed identifiers are preorder positions in the serialized tree, recomputed on structural writes. Unsupported decorated/multiline syntax remains in the source editor and original Mermaid renderer; merely opening a map never rewrites its payload. Source mode and visual mode share session undo history. The visual editor supports up to 500 topics, 40 levels and 1000 characters per topic; general source-length limits remain unchanged.

Canvas edits are local to the modal until save. Cancel leaves the Tiptap document intact, while save issues one normal rich-block transaction with the existing note save/version checks. Pointer capture starts only after a drag threshold so double-click editing remains available. Reparenting rejects cycles, root moves and excessive depth. Pan/zoom are transient; resize observers and delayed parsing are guarded by editor lifetime. This adds no backend methods, external access or file-format migration.

`web/editor-experience.js` mounts per-editor floating tools, command/reference suggestions, outline, local reading controls, find decorations and contextual table/code tools. Disposal follows the Tiptap editor lifetime. Outline positions and search decorations are derived, not serialized. Reading preferences use device/browser localStorage. File insertions map their destination through concurrent editor transactions; they do not reset the editor or replace typed content.

`web/history-ui.js` renders one selected revision at a time and compares sanitized top-level rich blocks using a bounded LCS in `web/editor-text.js`. Large comparisons fall back to whole-block additions/removals rather than quadratic allocation. Users may compare with a parent or the current snapshot. Partial recovery inserts selected serialized rich content at a mapped selection bookmark through normal undo/autosave; whole-note restore retains existing base-head validation. Quote annotations keep the existing schema: exact matches are derived from current text, ambiguous matches require a choice, and missing text is reported.

Clipboard File images without OS paths use `src/desktop/clipboard-import.mjs` through the existing sender/frame-checked desktop RPC only. The preload and main process bound image bytes to 32 MiB; the main process generates temporary paths, validates library membership, imports through the normal attachment path and removes temporary files. No generic Service or external Agent method is added. Source websites and remote image URLs are never fetched by this path.

## Local storage selection

`storage-location.mjs` resolves a device-local startup pointer next to the initial directory (`<anchor>.storage.json`). Existing launch arguments select the anchor; user-confirmed changes persist a pending action and apply at the next startup, not during editing. UI storage controls never enter external Agent RPC or shared revisions. Desktop can choose folders and restart; browser preview requires restarting its local server with the same anchor.

Windows preview implements `chooseDirectory` only in the authenticated UI adapter, outside Service and external Agent RPC. `src/preview/directory-picker.mjs` launches the system Windows PowerShell with a fixed, encoded STA script and no request-derived command arguments; the script returns a JSON path or null from a native folder dialog. The console is hidden, output and runtime are bounded, only one picker runs per server, and client disconnect/server shutdown abort the child. Desktop keeps Electron's native dialog. All root actions select first, then inspect and confirm; picking alone never schedules a storage change. Root and sync settings share the UI picker; independent backup and restore entries are retired.

`workspace-lock.mjs` gives each Service exclusive ownership using a PID/nonce file, with a separate anchor-configuration lock. An unchanged dead-process lock can be reclaimed; unknown/live owners fail closed. Legacy builds do not cooperate with this lock and must be closed before relocation. Missing databases in configured locations fail explicitly instead of initializing blank workspaces. Desktop and preview vault formats are not interchangeable.

Migration retains the source and requires an empty, disjoint local destination. Configured sync/backup overlaps, symbolic links and UNC paths are rejected. Startup rechecks identities and boundaries. A SQLite write reservation holds other writers while the SQLite backup API snapshots committed WAL content and managed files are copied, flushed and hashed. A second integrity check and asset hashes gate activation. Local asset/file-link paths within the old directory are rebased; stable IDs, events, preferences, grants and secrets are retained. Chromium cache, temporary uploads and opened-file copies are excluded. This is a same-device move, not cross-device synchronization or independent backup.

Incomplete destinations remain marked and cannot be opened. The startup pointer changes only after the new Service opens successfully; a migration or settings-write failure retains the original pointer. A crash before pointer commit may leave an unused completed copy, but never replaces or deletes source data. The old directory is a rollback snapshot and must not be used concurrently with the migrated copy. Source databases and startup metadata must not be uploaded through directory synchronization.

## Library directories under the root

The selected workspace directory is also the system root. The root picker resolves an empty destination to the existing migration workflow and an existing database to the open-workspace workflow. UI confirmation names the resolved action and submits that action, rather than silently changing its meaning if the directory later changes. Existing explicit migration/open controls remain available.

`library-directories.mjs` creates a direct child per library, with a small ownership marker and a relative-name map in `local_config.libraryDirectories`. Names are bounded and Windows-safe; unrelated folders, reserved names and sanitization collisions are never claimed. The stable library UUID remains independent of the directory name. Renaming library metadata, deleting or restoring a library does not rename or remove its folder. A missing mapped directory can be recreated, but a replaced marker or symlink is rejected. Filesystem failure during a new library save rolls back its knowledge revision and local mapping; partially created folders may remain but are never exposed as committed libraries.

Trusted UI state decorates libraries with local paths/errors and reconciles legacy/synchronized/restored library directories without rewriting events. External Agent library/record responses remain path-free. New UI and Agent attachment imports use the library's `attachments/<hash>` path; identical content in separate libraries may occupy separate files. Existing paths and shared sync/backup object staging remain readable. Migration preserves relative folder mappings and rebases attachment bindings under the new root.

The root SQLite database remains authoritative for notes, histories, authorization and shared consistency. Library folders are not standalone workspaces and do not enable filesystem auto-import. Ownership markers and local maps do not enter sync packets or independent backup revision data; another device derives its own safe directory layout.

## Note knowledge tree and local projection

`note-hierarchy.mjs` implements optional `parentNoteId` on formal notes. A library is the root and authorization boundary; a note may have both body and child notes. Local writes reject cycles, more than 16 levels, cross-library parents, stale bases and deletion of parents still referenced by children, including recycled notes and pending proposals. Titles are not identities and may repeat. The frontend exposes a note tree, parent selection and child creation; it does not expose filesystem folder management.

`web/note-tree-drag.js` handles trusted UI drag sessions: drop in a note's middle to become its child, at its upper/lower edge to place a sibling before/after it, or on the library heading to return to its root. Geometry and the observed tree snapshot stay stable during dragging. A per-session token excludes external payloads; target hints, cycle/scope/depth checks, Escape cancellation and edge scrolling are local UI state. Persistent sibling ordering is described below.

Open-note moves enter the existing per-tab autosave writer, with pending parent placement retained when capturing further text edits. Current and background drafts keep their existing base heads; closed-note moves use `noteMove` with the observed heads. Failed writes restore the uncommitted parent intent while retaining text for explicit recovery; conflict writes never auto-create a branch. Navigation and breadcrumbs refresh without rebuilding the active editor or attachment preview. Accepted parent changes mark the existing LocalHierarchy projection dirty: descendants follow the ancestry, dedicated originals move after copy/hash/binding checks, shared originals remain shared and external/extra files are retained. Saving placement is not proof that filesystem maintenance has completed; existing settings expose pending/errors and retry. No new Agent permission or filesystem API is introduced.

Synchronization preserves raw note revisions. A read-time tree detects concurrent cycles, missing parents and conflicting heads; affected notes remain discoverable at the root with an issue marker. It never silently writes repair revisions. Parent and ancestor references participate in external Agent scope and sensitivity checks. Direct note updates preserve placement; Agent hierarchy changes require a reviewed proposal.

The old folder protocol remains readable. At Service startup and after sync import, deterministic derived note and revision IDs convert folder histories into editable overview notes. Existing note placement and pending proposals receive additional revisions referencing those overview notes; original event bytes/hashes are untouched. Conversion runs transactionally, is restartable and produces identical events on multiple computers. Explicit later parentNoteId choices are not overwritten. Legacy folders remain historical compatibility records, never used as a new UI organizing model.

Proposals support optional local `key` and `parentKey`, resolved to stable target UUIDs before persistence, plus per-item reasons. Scope checks include virtual not-yet-created parents without trusting them to shadow existing records. Selected items are topologically ordered and written with the proposal receipt in one database transaction. A missing unselected new parent is an explicit error, never implicitly approved. Existing target base conflicts roll back the current selection. Previously accepted items remain untouched and pending parts can be revised.

`local-hierarchy.mjs` automatically projects saved content directly under each owned library directory, following the note tree with stable UUID suffixes and Windows-safe names. Full JSON retains rich structures, provenance and current branch heads; Markdown keeps body text (HTML remains HTML). A sole referencing note owns its original-file placement; multi-note references use a shared location instead of copying per note. Unattached materials stay at library level. SQLite still owns full edit history; these files are neither automatic import sources nor independent backups.

Dirty markers are committed with knowledge changes. An idle service interval maintains files automatically; failures are reported in system storage settings and can be retried explicitly. Shutdown waits for active projection; sync/retention waits for current projection and excludes concurrent runs. Unsaved editor buffers never enter the projection. Library creation itself creates its real root immediately, before any notes.

Originals move by copying into the managed classification tree, verifying the full hash, flushing, rechecking current heads/location/readers, then committing new bindings and a cleanup journal together. Cleanup checks ownership, no remaining bindings, active reads and source hash before deleting old managed bytes. External sources and user extras are retained. Generated text cleanup only touches previously recorded matching hashes and empty owned ancestors. Retry can reuse a verified destination after interruption. Relative projection maps survive root migration; synced content never contains these local paths. Automatic repeated checks cache local file fingerprints; explicit refresh rehashes originals.

Workspace scans and note-body derivatives still cost local space; very large libraries need future profiling. Upgraded workspaces now maintain their local projection automatically while preserving external sources and modified projection files. Existing unclassified notes remain top-level; no subject hierarchy is invented.

## Material management

The note-side panel is named "原附件". It reuses trusted asset metadata/detail methods and can link existing same-library assets or import local files. Link/unlink changes pass through the same per-note autosave queue and captured base heads as text edits; pending attachment arrays survive later text input and in-flight saves. Failure/conflict preserves drafts and pauses, without automatically saving a branch. Metadata refresh updates the side list without replacing the editor or an unrelated media preview; request identity prevents stale list responses from replacing newer associations.

`web/attachment-drag.js` adds native dragging from the attachment list into the current editor. A transient in-memory session binds the source asset, note and editor to a random drag token; arbitrary external payloads cannot supply an asset ID. The drop position maps through transactions during trusted metadata lookup, then inserts the existing image/video block or internal file link through normal undo/autosave. The active note, same-library association, deletion and conflict state are rechecked. Drag markers and edge scrolling are temporary and disposed on cancellation or editor destruction. No upload, new asset identity, shared schema or Agent capability is introduced.

The existing store automatically collects inline media/link references into `assetIds`. The panel distinguishes those from attachment-only associations and refuses to unlink an asset still used by body/source links. Unlinking an attachment-only association retains the asset, its bytes, immutable history and other notes' references. No shared schema or Agent permissions change.

`asset-management.mjs` serves the trusted UI catalog, detail, metadata updates and atomic batches. Existing asset `title` is a display name; `filename`, UUID, content hash, byte size and file binding are not changed by metadata edits. No shared schema fields or transport formats were added. Library reassignment clears obsolete folder placement; the existing local projection maintains managed paths independently.

The catalog filters by library, name/original filename/tags, type, local availability and reference/duplicate/conflict state; it sorts and returns pages of at most 200 entries. Local availability checks file type and size, not cryptographic identity; use/transfer still requires existing integrity checks. Duplicate hashes are hints, never automatic merges. Catalog rows scan all asset metadata, while current reference parsing is cached by the last reference-bearing event identity plus local dirty draft snapshots. Asset metadata batches do not invalidate that parsing cache. This is not a persistent indexed search engine.

Local asset recycling and cross-library changes pass a Store write guard covering all current branch bodies, inline rich links/media, pending/accepted proposal content, recycled records and persisted local draft snapshots. Unparseable rich references fail closed. Historical non-head revisions do not indefinitely prevent management. Recycle keeps original bytes and immutable history. Batch requests require all expected heads and commit in one SQLite transaction; any stale, referenced or invalid item rolls back the whole batch. Restoring an attribute history adds a new revision, subject to the same placement/reference protection.

Incoming immutable events are not rejected by the local reference guard: cross-device concurrent note references can arrive after a local move/recycle, and must remain intact for explicit review. Originals are not physically deleted by recycling. The local check is protection against known references, not a global lock across offline computers. Sensitive flags and all references remain subject to existing external Agent authorization checks. New catalog/detail/update/batch methods are UI-only; the Agent uses existing scoped search/read and proposes organization to the user.

## Versions

Every shared entity has a stable UUID. Revisions contain a distinct UUID, origin device UUID, device sequence, parent revision IDs, timestamp, deletion flag, schema version, allowlisted data and a canonical SHA-256 checksum.

New revision data is normalized to plain persistent JSON before business validation and hashing. Undefined object properties are omitted and undefined/sparse array elements become null; unsupported types, non-finite numbers, accessors, cycles and excessive structure are rejected. `insert` revalidates the serialized representation before any mutation. The global canonical function and existing hashes remain unchanged.

Earlier builds could hash undefined object properties which JSON storage subsequently dropped. On checksum mismatch, `revision-integrity.mjs` may reconstruct only allowlisted missing optional properties in memory (including known workspace tab and proposal data fields). A record is accepted only if this representation exactly reproduces its existing SHA-256. No persisted fields or hashes are rewritten. Search stops after 1024 candidates or a 32 MiB hashing budget, uses at most 64 candidate slots and caches at most 64 outcomes keyed by both original and current-content hashes. Unsupported/ambiguous causes remain errors; corruption is never accepted just because a record is old. Older clients cannot consume these compatibility-verified records, so both participants need the fix. `syncIntegrity` is a trusted, read-only local report; it does not scan cloud data or expose keys. Download scanning distinguishes missing shards from integrity failure.

The `heads` table is a materialized frontier of the revision DAG. Child revisions wait in `pending` until their parents exist. Parent/entity/type validation prevents cross-entity ancestry. Concurrent heads are preserved. User edits require the base heads they saw; stale editors cannot silently rebase. Explicit branch save and conflict resolution create new revisions.

Deletes are tombstone revisions, not file absence. Historical recovery creates another revision. Restoring an independent backup merges histories rather than replacing a database.

Shared entity kinds: note, draft, conversation, source, annotation, relation, proposal, workspace, asset, provider, model, usage, task, library, folder, agentPreferences. Conversation/provider/model/usage/task remain recognized for historical compatibility only. Proposal acceptance validates target bases and commits selected items with the proposal revision in a single transaction.

## User-owned libraries

Version 0.1.1 adds explicit `library` revisions. A fresh workspace has no libraries. New libraries use their UUID as an immutable `domain` scope; the display title and description may change without rewriting notes, conversations or history. Library metadata uses the same encrypted transport, conflict and backup mechanisms as other entities. All participating applications must be upgraded: version 0.1.0 does not recognize the new entity type.

Historical content without library metadata is exposed as a legacy library projection with a deterministic ID derived from its existing domain. Reading this projection creates no revisions. The first user edit persists metadata with that same identity and original domain, allowing concurrent edits on different computers to converge as visible conflicts. Model, provider and workspace metadata do not create phantom libraries.

Deleting a library is allowed locally only when it contains no content, including recycled content. It never cascades. Content arriving concurrently with a remote library deletion remains discoverable under a recovery-marked library; the user may restore the library. Historical note/backup formats remain readable without destructive migration.

Workspace-local settings include selected library, tabs, unsaved note drafts and reading positions. Historical chat state is not automatically erased but has no running UI or worker. Outgoing publications and incoming adoptions allowlist only id, recordId, title, domain and scroll. The old `__all_libraries__` discussion domain remains excluded from legacy library discovery.

## Current content sync (v3)

`current-sync.mjs` replaces runtime Git and independent backup. SQLite retains the immutable per-record edit DAG, stale-save guards, conflicts and restorative edits. There is no commit step or application-wide local version catalogue. All libraries, preferences and public device policies travel together; secrets, local paths, database files and device authorizations never do.

Known attachment descriptors do not by themselves authorize missing-object reuse. Local per-channel `confirmedObjects` retains exact object hash/size evidence from user batch/publication confirmations and inherited references in imported other-device manifests. The latter permits index-only devices to publish note edits; reimporting this device's own pointer is not new evidence. Planning persists evidence before replacing earlier plans. Publish ignores legacy `reusable` flags, rewinds to missing unconfirmed objects and regenerates them from local originals under the same space/batch limits. Even an unchanged snapshot requires those objects or valid reuse evidence. No manifest format changes or API-verified upload claims result.

Each device atomically replaces its own authenticated `current-<deviceId>.sscurrent` pointer in `StudySelfSync/v3/<key-fingerprint>`. Its manifest refers to immutable encrypted history shards (about 2 MiB) and binary attachment chunks (4 MiB). Each pointer is self-contained, including note modification history: new devices need only the latest pointers and referenced objects, not older manifests or Git prerequisites. Downloaded pointers are merged by stable event IDs and ancestry, never by device timestamp.

`sync-publication.mjs` writes and flushes one encrypted temporary pointer, then retries only replacement failures with EPERM/EACCES/EBUSY. Seven asynchronous backoffs (200, 400, 800, 1600, 2000, 2000, 2000 ms) bound retry count; short wait slices check Pause. Other I/O failures are not relabeled as contention. The old pointer is never deleted as a fallback. Exhaustion retains the frozen publication and old pointer; a restart/continue retries the same snapshot, excluding edits saved during the wait. Local progress distinguishes object generation from pointer replacement. Completion and exported flags are set only after replacement succeeds. Cleanup only attempts this invocation's temporary file; a cleanup failure is appended to the original error, and the encrypted `.partial` remains ignored by discovery. There is no sweep, chmod, client termination, protocol change or cloud-success inference.

`sync-state.mjs` validates histories and device policy DAGs before mutation. Pull validates all downloaded manifests and metadata, assembles required originals, then transactionally applies events, asset bindings, device state and import identity receipts. A failed database transaction leaves current knowledge intact; verified file objects can be reused on retry. Index-only imports explicitly leave originals unavailable.

Publication freezes saved events in a persistent local plan. `statfs` estimates free bytes, additional encrypted-object bytes and a 64 MiB reserve; batches default to 256 MiB, bounded again by live free space before each write. Cursor progress persists after every object, and pauses/errors survive restart. Previously generated objects released through the official client require explicit batch-upload confirmation before finalizing a new pointer. Published descriptors can reuse existing immutable cloud references without fetching every old original. No cloud success is inferred from this bookkeeping.

`resumable-files.mjs` persists `.v3.partial` data and per-hash checkpoints. A chunk is checkpointed only after flush. Restart verifies each checkpointed prefix chunk, truncates any untrusted tail, and resumes at the first invalid/missing chunk. Missing cloud copies of an already verified prefix do not prevent continuation. Per-chunk authentication, full-file hashing and atomic promotion precede asset binding. Free-space checks and cooperative pause retain useful partial bytes.

`received-objects.mjs` reports the local assembly directory on demand through a trusted UI method, with paginated entries and explicit resume/read/binding/cleanup/unknown states. Inspection reads metadata only and does not follow directory links or expose paths to external Agents. Directory organization and permanent-deletion finishing remove this directory only when it is empty and has no local asset binding, checkpoint or local-file-link reference. Removal uses non-recursive `rmdir`; failure is retained for retry. Nonempty originals continue through existing content-hash and reference checks; unknown files and interrupted receives are never treated as disposable cache. The settings panel refreshes independently of unsaved preferences.

Device retention guards remain: conflicting primary roles block release, secondaries require a current-primary hash receipt, no unsent changes, no pinned/active/local-file-link references, and a managed verified path. Primary originals remain protected. Per-note history restore does not require Git; cloud-level history is managed through Baidu. Restored old manifests on an existing workspace merge without silently discarding later edits.

Device administration (`device-management.mjs`) adds an optional immutable `control.management` DAG. Entries bind actor, role epoch, target, parents, action and (only for rename) name. Only the current unique primary may create them through the trusted `deviceManage` service method; the Agent HTTP/MCP surface does not expose it. A control digest protects stale confirmations, and request IDs make identical retries idempotent. Device labels and suspension are projected by causal ancestry, never wall-clock order; conflicting names retain candidates, and conflicting suspend/resume events keep the device paused until the primary resolves them. Local-device naming also follows primary ownership once a primary exists.

Transfer is requested by the old primary and accepted on the target after merging current content and checking available originals. The accepted role references the request and management heads. Until acceptance the old primary remains responsible. Offline acceptance concurrent with cancellation or replacement produces a role dispute, not an implicit winner; a participant must explicitly recheck and resolve it. Role/management dependencies are validated together for missing references and cycles. A frozen publication cannot continue after its role or management basis changes.

Manifests carrying management entries use format 5 in the existing v3 channel and include an `erasures` array (possibly empty), preserving the v4 erasure machinery. v3/v4 remain readable; management in a downgraded manifest is rejected, and old clients reject format 5. Updated receivers first validate/merge control state, skip knowledge payloads from known suspended publishers, and let a suspended local device receive only management state so restoration remains possible. Already received knowledge, local edits and originals remain intact. Publishing, hydrating, eviction and transport-deletion cleanup are blocked on suspended devices. These are application-level rules for updated cooperative clients sharing a channel key, not cryptographic device revocation, remote erasure, enforcement before offline peers receive policy, or protection against a malicious key holder. All peers must upgrade before using administration.

Retired v2 journals recover their knowledge payload/bindings directly into SQLite; old repositories, backups and directories remain untouched. No active Service method imports Git or `BackupManager`. Legacy modules below remain test/reference compatibility only. See [decision 0006](decisions/0006-current-content-sync.md) for current recovery boundaries.

## Git versions and v2 handoff (retired)

`git-versions.mjs` maintains one bare repository per library scope plus `__shared__`. The JSON snapshot preserves original immutable revision IDs, rich content, provenance and file identities; binaries never enter Git. Moved records include required ancestors and the outbound move boundary in their previous scope, but not subsequent edits owned only by their new scope. Whole-library restore cannot reclaim an entity currently belonging to a different library. The repository is not the project source repository and never travels directly.

`v2Journal` durably records the frozen snapshot, intended parents and optional import bookkeeping. Recovery deterministically creates/reuses the commit, updates the local ref, then transactionally imports events, file bindings, import receipt and pointer. Pending journals prevent new edits. Restores save restorative revisions and the operation journal together; they do not rewind a ref over later history. Backup-restored tips are retained as archive refs and become parents of the next local commit.

`git-sync.mjs` was the v2 Service transport. Only explicit UI commands committed, published, scanned or imported. Publishing froze the submitted commit, using a full bundle initially and a prerequisite-based incremental bundle thereafter. A persistent publication ID and immutable object names supported retries. An incoming bundle had to verify, unbundle and pass Git fsck before its snapshot was accepted. Merge retained both Git parents and conflicting entity heads; dirty editor tabs or uncommitted scope changes blocked pulls. No timer imported incoming files.

`sync-objects.mjs` implements a directory channel with no cloud observation/control capability. The namespace is `StudySelfSync/v2/<key-fingerprint>`. Manifest, bundle, receipt and original chunks are all authenticated encrypted objects. Binary framing is an 8-byte format marker, 12-byte nonce, 16-byte GCM tag and ciphertext; AAD binds object identity. Attachments use SHA-256 plus 4 MiB chunks, full-file validation and local `received-objects/<hash>` staging/retention, compatible with earlier local bindings. Missing/truncated/unauthenticated objects never become complete records. Scan presence and size checks are only discovery, not integrity evidence. Normal import requires all current snapshot originals; explicit secondary index-only import leaves files unavailable.

Device announcements and primary-role DAG are shared in the separate scope. Local addresses, credentials and release paths are not. Conflicting roles disable eviction. Primary receipts cover verified file hashes under a committed role epoch, not cloud upload. Secondary eviction additionally requires explicit confirmation, clean versions, no active media read or pinned alias, no local-file-link reference, a known handoff manifest and a managed content-addressed original path. The app never deletes transfer files for space management. Primary originals are currently all protected; historical orphan eviction remains deferred. The retired client questionnaire is no longer an API or release prerequisite; existing local questionnaire records are left untouched and provide no release authority.

The first explicit commit lazily migrates existing revisions without changing IDs, SQLite history or originals. Old and new namespaces do not mix. Old cloud packets must be received with the old version before switching; no automatic old-packet importer is exposed in v2. See [decision 0005](decisions/0005-git-encrypted-handoff.md) for limits, backup compatibility and transport responsibilities.

## Legacy folder transport (inactive in Service)

The transport directory is disjoint from the local database directory. A 256-bit pairing key creates a channel fingerprint. Transfer envelopes use AES-256-GCM with authenticated schema/kind/sender/packet metadata. They are written through a uniquely named temporary file, flushed and renamed to `.ssync`; readers ignore partial files, verify authenticated payloads and content checksums, and deduplicate packet/revision IDs.

Large notes are batched by byte size. A received parent may unlock pending children. Receipts acknowledge only committed revisions, not unseen or pending children. Recipients create encrypted receipt packets; their eventual arrival supplies the only remote-received status.

No lock files, global mutable manifests or online coordinator are required. No operation assumes both computers are online. No cloud upload success is inferred. Baidu Sync Space is the user-accepted transport dependency, not a product awaiting requalification. StudySelf must still handle delayed, missing, repeated and damaged files correctly. Optional real-device integration records do not gate development or replace application integrity tests.

Local states: `local` = committed revision not yet published, `waiting` = an encrypted record was written to the configured directory, `received` = a different device acknowledged it (or this is an imported revision). Attachment availability and backup completeness are separate.

## Legacy attachment protocol (retained for compatibility tests)

Shared metadata uses a stable asset UUID, SHA-256, byte length, media type and original filename. Local bindings never travel. All imported files, including standalone and recycled assets, travel through authenticated packets and are stored locally on each computer. New files up to 4 MiB use the legacy `asset` packet; larger files use `asset-chunk` packets with fixed 4 MiB chunks, index/count, full-file hash, size and individual chunk hash. Legacy whole-file packets up to 16 MiB remain readable. Both computers must upgrade for chunk support. URLs and device-only external file bindings are not automatically downloaded or uploaded.

Publication checkpoints and incoming packet references are device-local SQLite settings. Interrupted publication reuses verified immutable packets. Incoming chunks may precede metadata or arrive out of order; the receiver streams authenticated packets into a local staging file, verifies the complete SHA-256 and atomically promotes it before binding asset IDs. It does not keep an additional plaintext chunk cache. Whole-file failures retain retry information without presenting partial attachments. Missing/corrupt local originals do not create deletion revisions or block unrelated notes; a cycle reports local file availability separately from note receipts and unverified cloud upload status. File packets are retained for offline/new devices. Automatic transport garbage collection and remote full-file receipts are not implemented; therefore no claim of zero duplicated disk use or remotely complete original files is made.

Successful local file hashes are cached against device-local path, file identity, size, modification time and change time, avoiding a full video rehash on every timer tick. A changed signature triggers a new hash check. Complete incoming assembly always verifies the full content, independently of this cache. Retained incoming packet references allow rebuilding a lost receiver copy, including legacy small files; they do not authorize deleting transport packets.

Processed packet scan fingerprints are also device-local. Only unchanged files whose packet digest still matches the persisted receipt can skip decryption; small-file packets are reopened when their local original needs repair. Changed signatures re-enter authentication and immutable packet-ID collision checks. Incomplete large files still assemble from their validated packet references, never from the scan cache alone.

Pinned means the application should keep the local object. There is currently no automatic object eviction, so unpinned files are not automatically deleted either.

## External Agents and Skill

### Rich note content

Content layout uses a separately validated `data-ss-layout` JSON attribute (width 15-100 percent, height null or 60-1600 pixels, align left/center/right) for rich media. Ordinary text, tables, callouts and file links use continuous document flow, with no fixed-size editing boxes. After HTML sanitization, the browser unwraps legacy `section[data-ss-container]` nodes recursively while preserving every child and empty paragraph; mixed text/media rows are unwrapped in reading order, while figure-only `div[data-ss-row]` remains horizontal. Initial loading, HTML paste and read-only history use the same conversion. The runtime editor no longer defines text layout boxes. Merely opening does not write a revision; a subsequent user edit saves continuous content through normal autosave, leaving original history and hashes untouched. Core validators still accept the old format for compatibility and synchronization. Read-only hydration derives media styles from validated attributes; Markdown preserves remaining rich-media layout wrappers.

Rich-media node views present unframed content with internal captions and hover/focus actions. A stationary primary press of 0.5 seconds starts a pointer-captured floating preview for every rich block; movement before activation cancels the hold. Left/right drop targets form media rows and upper/lower targets reorder blocks. Eight transparent edge/corner regions resize rich media without a dedicated grip. Ordinary text has no such regions or gesture listeners, so native selection, paragraph splitting/joining and undo remain available. Escape, pointer cancellation, window blur and node destruction clean up previews and restore uncommitted sizes. Native video controls and action buttons do not initiate holds. Gesture previews never enter note HTML or saved history.

DOCX attachment previews use the existing trusted `assetContent` read (24 MiB limit), detecting old generic MIME records by filename. A separate bundled Worker uses Mammoth 1.13.0 and JSZip 3.10.1. It checks actual decompression streams against 64 MiB/2,000-entry limits, caps HTML at 12 MiB and is terminated on cancellation or a 20-second timeout. External file access and embedded style maps are disabled. DOMPurify restricts generated markup; only embedded PNG/JPEG/GIF/WebP images survive, and external links are inert. A sandboxed `srcdoc` iframe has no script or same-origin permission and an internal restrictive CSP. `srcdoc` also avoids blank Blob document navigation in the in-app browser. This is a reflowed reading view, not original Word pagination. Conversion changes neither the source asset nor note history. Source previews reveal themselves after long lists, can expand, and discard stale reads without rebuilding the editor. Modal close removes the iframe and releases resources. The preview server serves only the named worker asset; no new Agent or filesystem endpoint is added.

Horizontal targets also include whitespace beside a media node within its parent bounds and vertical extent. Only an ancestor hit can claim this whitespace, preventing text and adjacent containers from being treated as a side target. The nearest horizontal edge wins and its vertical indicator is at least 36 pixels tall. Explicit media rows do not wrap or switch to columns at narrow widths: saved percentage widths form flex bases and shrink when necessary. Layout attributes, source payloads and the existing row format remain unchanged; opening a note does not save a layout migration.

Text drop targets resolve visible line boundaries through ProseMirror coordinates, including hard breaks, soft wraps and inline marks. Moving to such a target removes the source, maps the destination through that transaction, and inserts the original rich node with schema-aware paragraph splitting. A boundary hard break becomes the split; extra blank lines and marks remain. Media-row extraction unwraps a sole remaining sibling. Nested list/quote/table positions can be moved again; code blocks retain whole-block placement. The complete move dispatches once for undo/autosave, and cancelling never edits the document.

File drops import only the supplied files through the authenticated preview upload or Electron's `webUtils.getPathForFile` preload bridge and trusted IPC. Images/videos embed stable asset IDs, other files become internal attachment links. Browser uploads retain the 128 MiB per-file limit; desktop imports use existing path-based streaming. Imports keep a mapped insertion position while the user edits; navigation/close actions are held until the batch completes, and individual failures leave successful imports intact. Dropping files never navigates the browser to their local path.

`web/note-autosave.js` serializes writes per note after a 1.5-second edit pause. Each request captures the draft and its base heads. Later edits remain dirty and use the returned heads for their next write. Successful saves update status without rebuilding the editor, preserving selection, undo and media state. Failed/conflicting requests pause automatic retries, retain local drafts, and require manual action; only an explicit manual confirmation writes a concurrent branch. Workspace draft snapshots are queued in order, independently of note revisions. Closing a dirty page still warns, and local save does not publish cloud content.

HTML note content has additive `figure[data-ss-block]` nodes containing versioned JSON (`v: 1`). Media refers to stable asset IDs; diagrams keep Mermaid source, formulas keep LaTeX, canvas blocks keep bounded structured shapes. Existing event schemas/checksums are unchanged; reading history does not normalize old data. New note/draft/source writes collect embedded assets. Core parsing uses parse5 (and marked for Markdown), independently of browser sanitization and declared reference arrays. Agent authorization follows embedded internal links/media and source URLs on every current branch and historical revision.

Rendering uses Tiptap task/highlight/custom nodes, KaTeX with trust disabled, Mermaid strict mode plus sanitized SVG, and Konva for canvas editing. External images/scripts/iframes are not accepted in note HTML. JSON characters that resemble XML delimiters are escaped without disabling sanitization. Atom-node views ignore display-only DOM mutations so asynchronous rendering cannot rewrite serialized content. Markdown export preserves raw rich-block HTML but does not bundle original assets or promise third-party rendering. Peers need the updated editor before editing rich notes; older editors can discard unknown nodes.

The preview adapter exposes authenticated `/media/<assetId>` GET/HEAD with single byte ranges, strict Host/Origin checks and no CORS. Desktop uses a `studyself-media://asset/<assetId>` protocol with a raster-image/video MIME allowlist. Both validate record availability, local regular files, size and hash before streaming. The content stores neither temporary URLs nor media access tokens. Large video startup may require a full hash scan; missing files remain visible as unavailable rather than deleting content.

Portable links use `studyself://note|asset|local/<UUID>`. Local-file UUID bindings live only in `local_config.localFileLinks`; paths never enter note revisions, workspace publications, transport, backup or Agent RPC. Only the desktop trusted UI can choose a binding. Opening requires native confirmation, local regular-file checks and a document/media extension allowlist; executables, scripts and UNC paths are excluded. Browser preview cannot directly open these bindings and supports managed attachments instead.

### Authorization and writes

`agent-access.mjs` owns a separate, default-off loopback MCP listener. Desktop and preview share this implementation. The listener persists its local port, checks Host, rejects Origin, limits body size and does not enable CORS. Only `/mcp` is available; the retired `/v1/rpc` returns 404 and never executes a business call.

Per-Agent random 256-bit bearer tokens are displayed once; only SHA-256 hashes and metadata are stored locally. All valid credentials cover current and future libraries, sensitive material, and existing read/collect/propose/edit/trash capabilities. Startup upgrades surviving legacy credentials without changing their hashes or expiry. Revocation transactionally deletes the grant, its audit entries and idempotency receipts; startup also removes legacy revoked entries. Knowledge revisions and other credentials remain. Revocation/expiry is checked after reading the request body and before executing tools. System configuration, files by arbitrary path, secrets, shell commands, preference writes, permanent deletion and approval remain UI-only.

Every current branch, historical revision and referenced source/asset/target must exist in an available library. Cross-library and sensitive reads are permitted, while missing/deleted-library references remain invalid. Files are hash-checked, addressed by asset ID and bounded to 16 MiB; no absolute paths are returned. Full access does not bypass stale heads, preference conflicts, hierarchy rules or integrity checks.

Mutations carry requestId, preferencesVersion and, for updates, exact base heads. The durable local agent_requests receipt and writeRaw revisions commit in one SQLite transaction. A repeated request returns the original result only when the digest matches and current authorization still permits access. A changed payload with the same ID fails. No network inference happens in this application. A bounded audit log stores operation names, grant IDs and outcome codes, not request bodies or credentials.

The fixed-ID agentPreferences entity synchronizes/backs up like other versioned content. It does not create a library. Its effective version hashes the maintained Skill baseline plus current preference heads. Concurrent preference versions suspend new Agent writes until user reconciliation. Adding this type requires every sync peer to update; historical schemas/hashes remain unchanged. Credentials and receipts remain local and are excluded from backup and transport.

Canonical Skill files live in skills/studyself-organize, included as application resources. bootstrap returns the latest Skill text, API guide, version and effective preferences. UI ZIP export contains a snapshot plus the dependency-free Node client. User requirement changes update this maintained source; installed copies fetch current guidance but are not overwritten automatically. Local installs receive no token or model configuration.

Built-in model, pricing and conversation workers were removed. The user subsequently authorized deletion of their stored history. Service startup removes conversation/provider/model/usage/task events, heads, queued payloads, known provider/probe/attempt configuration and secret:api credentials. Historical validators remain solely to recognize old formats. Current imports replace retired payloads with content-free erasure receipts, including later revisions produced by an old peer; they never execute or restore the retired records. Standalone Store/retired transport modules still support format fixtures; they are not the current Service runtime.

Erasure receipts may carry purpose=retired-ai (only for retired AI types or workspace). Old shared workspace histories containing chat fields are replaced with sanitized histories under deterministic new entity/revision identities; note drafts and positions survive, old hashes remain immutable, and all peers derive the same replacements. Local note tabs retain unsaved drafts. Existing note links to erased conversations remain unavailable links; authorization checks may skip a verified erased AI target but do not reveal its content. Imported files and external Agent credentials/preferences are not removed. Startup awaits physical cleanup before exposing the workspace; failed file cleanup remains retryable through the existing settings entry. Peers must update together. Cloud historical copies, retired archives and external exports require separate handling.

## Backups (retired compatibility module)

There is no current backup UI, Service method or idle backup scheduler. The following format description is retained for old data and compatibility tests; it is not an active product workflow.

A backup directory contains `revisions.json`, `manifest.json` and content-addressed original files. It excludes local databases, device identities, pairing secrets and API credentials. Revisions and files are verified before restore; the attachment files are staged before committing database history. Missing or deferred originals stay explicit in the manifest.

Format 1 now optionally includes verified per-scope Git bundle descriptors under `git/`. Archive refs preserve original commit IDs; restoring merges knowledge and device-role history without replacing current pointers or silently changing the new device identity. Old manifests without Git remain supported.

Backup content is currently plaintext and may only be generated outside the configured sync tree. Do not upload it unencrypted; cloud encrypted backup is not implemented. `localComplete` does not imply `cloudVerified`.

## Attachment Identity Reuse and Reviewed Merge

Trusted `assetCatalog` / `assetDetail` responses include a local `storage` projection derived from existing asset bindings. It reports the workspace root, actual directory/file names, availability and known hierarchy placement. Directory facets aggregate the filtered library scope before pagination; a selected ancestor filters only those existing bound paths. No filesystem directory enumeration, automatic reorganization or path-based arbitrary file read is performed. The UI exposes a collapsible directory filter and copy actions; these paths are excluded from shared record data and external Agent responses.

Trusted UI imports serialize per store and reuse an active, nonconflicting attachment in the same library when full SHA-256 and size match. Existing organized originals are verified and kept in place; metadata and pin state are preserved. Missing originals may be rebound after full verification. Explicit `duplicateMode: separate` creates an independent identity. Recycled/conflicting/cross-library identities are excluded. Agent `assetWrite` retains its own request-idempotency contract.

`asset-merge.mjs` previews 2–100 same-library, same-content identities, including current branch, draft, proposal and recycled references. The chosen identity retains its name; tags are unioned and sensitivity/pin flags cannot be reduced. A snapshot token binds assets, references, proposed writes and blockers. Dirty, conflicted, cross-library or unsupported references block execution. HTML edits target parsed attribute source locations; Markdown edits target parsed direct links and leave code unchanged. Unsupported reference forms block instead of reserializing or dropping rich content.

Confirmation rechecks the token and target original, then atomically creates reference revisions and soft-deletes redundant records. Failed writes roll back the entire operation. Import/merge work is coordinated with background directory maintenance and sync. Previous revisions and original bytes remain; historical references keep old IDs and may require restoring the old attachment for preview. This is identity consolidation, not physical blob garbage collection. No alias schema or new external Agent authority is introduced; concurrent peer changes remain immutable conflicts.

## Note Sibling Order

The trusted note tree offers before/after sibling zones and a middle child zone. Optional `noteOrder` stores exact rational ranks as decimal integer strings. Ranked siblings precede unranked siblings; unranked siblings retain title/ID order. Tree output is depth-first so children remain contiguous. Existing event bytes and hashes are unchanged; peers must upgrade before receiving the new field.

`noteMove`, or trusted `save` with transient `notePlacement`, verifies the source heads and a complete destination-level snapshot in one SQLite transaction. It initializes unranked destination siblings only when needed, assigns the moving note a rank between neighbours, and normalizes equal concurrent ranks only after the same checks. No-op positions create no unnecessary ordering revisions. Concurrent moves of the same record remain explicit branches; identical ranks on different records use stable ID tie-breaking.

Open tabs queue placement alongside text in the existing serial writer. Ordering responses update other affected local tabs only when their base heads match. An already dispatched stale sibling save still stops as a conflict; input is retained. Failure rolls back all order writes and removes the pending placement intent, retaining text. Reordering alone never renames note directories or moves originals; changing parent uses existing local hierarchy maintenance. External Agents retain existing order and cannot invoke trusted movement methods. No new cloud or Git dependency is involved.

## Draft Archiving And Review

`draft-workflow.mjs` derives a draft's processing state from reviewed references, with a cache keyed by the latest inserted event. It does not mutate the source draft or introduce a new synced entity type. Direct archiving is a trusted `draftArchive` transaction: validate source heads and unsaved local tabs, select an active library and a valid parent, copy the complete draft data into a new note, retain source/asset IDs and sensitivity, and record `draftOrigin:{id,versionId}`. The target UUID is derived from the source identity and revision. A local retry returns the existing result; concurrent device writes to that identity remain conflicting revisions. Original drafts, history and files remain; cross-library archiving does not move asset ownership.

Proposal items may carry `draftRefs:[{id,versionId,complete?}]`. Omitted complete means partial extraction. Review validates current source heads and dirty source/target tabs inside the same SQLite transaction as all selected writes. It adds draft provenance to sourceIds, propagates source sensitivity and records acceptedVersionId for the exact created note revision. A complete plan is processed only when every item for that draft revision has a valid confirmation receipt and usable result; partial extraction remains partial even after its items are accepted. A new draft revision returns to pending, keeping links to older results. Missing/conflicting/deleted results do not imply success; conflicts in proposal evidence prevent completion. One complete reviewed plan can finish a source without auto-accepting alternate proposals.

The trusted UI exposes a destination dialog, pending/partial/processed filters, linked plans and results. It flushes source edits before direct archiving, rejects changes after the dialog opens, retains the existing editor for filtering/status updates and defaults to pending/partial drafts. Search includes processed drafts. Sidebar draft counts reflect remaining work. Metadata is shared through existing immutable v3 events; old events are unchanged, and all receiving clients must support the new fields. Local hierarchy projection handles the resulting formal note normally.

Agents may submit versioned draft references with proposals and revise only pending items. They cannot remove existing source IDs from pending associations, write direct-archive provenance or confirmation receipts, or call archive/approval methods. Both current and referenced historical draft content are included in recursive authorization, and trash protection follows these references. This is an audit of user-confirmed coverage, not a claim that software can independently prove semantic completeness of extracted knowledge.

The trusted `proposalCleanup` method recycles only a nonempty, fully accepted, conflict-free proposal at the expected heads. It rejects dirty proposal tabs, creates a regular deletion revision transactionally and recognizes retries of the same deletion. The UI replaces approval/edit actions with cleanup once all items are accepted and links to the resulting notes. Recycling and restoration do not rewrite notes, sources or files. Draft workflow derivation continues reading recycled proposal evidence. Valid historical `acceptedVersionId` and `draftRefs` pairs establish reverse dependencies from drafts to proposals for permanent-trash protection, with the same check applied before remote erasure. Eligible dependency groups can still be cleared together. No event fields or transport format change; all devices should update to enforce the additional permanent-deletion protection. An older client that already erased the only confirmation evidence cannot have it reconstructed by this guard.

Node tests simulate separate profiles and transfer directories, reversal of directions, concurrent edits, dependencies, replay, corrupt transfers, deletes/restores, small/large files, partial approvals, backups, external Agent privacy boundaries, request deduplication, preference versions and workspace adoption.

## Local MCP Adapter

`agent-mcp.mjs` uses the official MCP SDK with a stateless Streamable HTTP transport on the Agent port at `/mcp`. Each request validates Host, rejects Origin and authenticates the local Bearer credential before bounded body parsing; tool callbacks reauthenticate before calling `AgentAccess.dispatch`. The exported dependency-free client performs MCP initialization, tool discovery and calls against the same endpoint. It never falls back to the retired RPC or retries business writes automatically.

Tools are named and schema-validated. Valid credentials discover all existing Agent tools. Write arguments carry the existing preference version and request ID; native MCP clients and the script share transaction receipts. Tool failures preserve known business error codes without exposing filesystem paths. The server emits JSON responses, does not retain sessions, and refuses batches, standalone SSE GET and session deletion; SDK transports are closed with the response. System RPC, approvals, erasures, configuration and credential management remain UI-only.

`web/agent-mcp.js` owns the single MCP connection section, its enable switch, endpoint and copyable Codex / generic MCP configurations without secrets. Grant forms only collect name and expiry; the list shows all-library access and removes revoked entries. Skill bootstrap is the live source of protocol and preference instructions. The SDK and Zod are production dependencies for Electron and preview; local source verification does not imply a rebuilt installer or third-party client certification. See [connection guide](agent-mcp.md).

## Built-in Skill Management

系统设置使用 `web/skill-manager.js` 管理唯一内置 `studyself-organize` Skill，文件预览只读，偏好和历史仍使用原 `agentPreferences` 不可变实体，不新增共享类型。用户补充不会写回随应用发布的文件。历史取回只是编辑操作，后续保存校验基础版本并创建新记录；过期保存需对照并明确选择当前编辑，不静默覆盖。页面切换和保存期间的输入由管理器保留。

受信任 `agentSkill` 返回固定文件集合、当前偏好、内置内容哈希、组合导出版本和本机最近生成信息。`agentSkillExport` 拒绝偏好冲突，冻结当前文件/偏好并记录本机生成元数据；外部 Agent 无权调用。ZIP 附带 `manifest.json` 与偏好快照，`skillVersion` 与 bootstrap 对齐，`exportVersion` 同时覆盖内置内容和偏好版本。不执行文件内脚本。外部 Agent 仍须在每批写入前读取 bootstrap。

`SkillInstallations` 仅通过受信任界面的 `skillInstall*` 方法操作用户明确关联的已有目录，不扫描宿主安装。固定五个文件与 ZIP 导出内容一致；额外文件不读取或修改。安装位置拒绝软/硬链接及工作区、源码 Skill、同步目录，路径只在本机管理界面出现。`local_config.skillInstallations` 保存摘要、模式、上次副本与恢复日志，不新增共享实体。随机安装标记限制单工作区归属，目录锁防止多个进程同时写入。

安装缺少固定文件时状态为 `incomplete`，返回 `missingFiles`，自动更新不执行写入。新目录仍须验证 SKILL.md；已关联且归属匹配的目录即使缺少入口，也可通过 `skillInstallPreview(action=repair)` 预览确认补全并更新完整当前包。现存入口仍必须通过身份校验，不能凭标记覆盖其他 Skill。修复复用更新日志、文件快照、偏好版本和归属重验；额外文件保留。恢复前提示目标副本的缺失项，恢复到不完整状态也不能触发自动补全。

预览令牌绑定文件快照、关联设置和内置/偏好版本，五分钟有效，确认重验。每文件原子替换，manifest 最后写；不承诺整个目录对第三方读取原子可见，更新时应暂停使用该 Skill。变更前持久化 before/after，失败/启动时只对仍匹配这两份内容的文件回滚，遇到外部新修改保留现场。上一份受管文件可恢复，恢复后关闭自动更新。应用运行期间每分钟检查，只有明确开启自动更新且文件摘要未被手改时才更新；设置导航显示待处理数。成功仅证明安装文件已写入，不证明宿主已重载，连接/授权配置不改。解除关联不删除安装文件。

## Verification

### Desktop Exit Check

The close event starts a request-scoped handshake (`exit-check.mjs`). The preload exposes a fixed exit-request listener; trusted renderer RPC supplies `exitStatus`, `exitCancel` and `exitFinish`. Renderer state covers all note/draft tabs, composition, imports and unsaved preferences. An existing editing dialog is never replaced. Acknowledgement timeout leaves the window open. Cancelled, repeated or previous-page requests cannot close the application.

Save-and-exit flushes each note's existing serial saver, allowing an explicit retry without manual branch creation. Failed or conflicting drafts remain editable. Workspace persistence must finish, followed by a fresh renderer check and a main-process check of stored dirty tabs and active writes. Background timers/Agent listening stop only after accepting the final close. Pending publications and manual upload confirmations are independent of local saves; ordinary exit neither publishes nor installs updates. `callResult` carries structured errors across the isolated preload so conflict codes survive Electron's error serialization; the older `call` remains available for compatibility.

Storage restart uses the same request-scoped handshake with `storage-restart` intent. Both initiation and final acceptance check imports, cleanup, active original reads and other IPC; the pending storage change must still exist. Finalization awaits database/lock closure before `app.relaunch`, and the IPC awaits that asynchronous result rather than trying to serialize a Promise. No direct timed `app.exit` bypass remains. The isolated desktop regression also inserts an import after the dialog opens to test the final gate.

### Cleared Legacy Records and Empty Directories

`deletionStatus.legacyCleared` counts old purged heads and their retained history across all scopes. The trusted trash preview/confirmation accepts `legacyOnly`, covered by its confirmation digest, so legacy cleanup cannot silently expand into ordinary trash. Existing reference, conflict, transaction and erasure transport protection remains in effect.

`empty-library-directories.mjs` exposes a separate trusted preview/confirmation for mapped marker-only directories. It checks current libraries, all historical events, pending/rejected imports, workspace tabs, bindings and tracked file jobs. Active empty libraries and unknown or nonempty directories are retained. Execution rechecks the digest and individual candidates, removes only the verified marker and then uses nonrecursive directory removal. Failures preserve replacement files and attempt exclusive marker restoration; partial results persist locally. A missing marker after a process crash is treated as unknown ownership and never auto-deleted. No startup sweep or external Agent method is added.

Playwright browser tests cover real editing and task navigation. Native tests additionally cover packaged Electron startup, preload IPC, SQLite and Windows encryption. All test material is generated under `artifacts` and does not use a personal cloud account or a paid model.
